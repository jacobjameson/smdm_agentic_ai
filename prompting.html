2 · Prompting & Directing Agents

How to ask well, scope context, and stay in control

Module goal: Learn the handful of prompting habits that separate a frustrating agent session from a productive one — and meet CLAUDE.md, the file that makes an agent behave like it knows your project. Ends with Exercise 1. · Slides

Prompting is specification, not incantation

There are no magic words. A good prompt is just a clear specification of intent, context, and constraints. The mental shift: talk to the agent the way you’d brief a capable new research assistant who is fast, literal, and doesn’t know your project yet.

Four ingredients turn a vague ask into a good one:

Ingredient Weak Strong
Goal “clean the data” “drop rows with missing age, and recode sex to a factor with labels Male/Female”
Context (none) “the raw file is data/raw/cohort.csv; the cleaning script is R/01_clean.R”
Constraints (none) “use tidyverse, keep it readable, don’t change the column names downstream code expects”
Done-condition (none) “it works when 01_clean.R runs without warnings and writes data/clean/cohort.rds”

Six habits that make agents work

  1. State the goal and the done-condition. “How do you know it’s finished?” is the single most useful sentence to add.
  2. Point at the context. Name the files, the function, the error. Agents are great at reading your repo — tell them where to look instead of describing from memory.
  3. Plan before acting on anything non-trivial. Ask for a plan first: “Before editing, tell me your approach and which files you’ll change.” Then approve or redirect. Cheap to steer early, expensive to unwind later.
  4. Work in small steps. One change, review, next. Matches Jacob’s “small testable steps over big rewrites” default and keeps diffs reviewable.
  5. Make it show its work. “Run the tests.” “Show me the diff.” “Print the first 5 rows.” You’re verifying, not trusting.
  6. Correct with specifics. Not “that’s wrong” but “the join dropped 12 rows — use a left join keyed on id.” Precise feedback closes the loop fast.
TipDemo (do this live)

Take a deliberately vague prompt (“make a figure of the results”) and a specified one (“plot mean cost by treatment arm as a grouped bar chart with 95% CIs, colorblind-safe palette, save to figs/cost_by_arm.png at 300 dpi”) — run both and compare. The difference sells the whole module.

Scope the context deliberately

The agent can only reason about what’s in its context window. Two failure modes:

  • Too little: it guesses about files it hasn’t seen and invents column names. → Point it at the files.
  • Too much / stale: a long, wandering session accumulates dead ends and the agent loses the thread. → Start a fresh session for a new task. A clean context is often the fix for a confused agent.

Rule of thumb: one session, one coherent task. When you switch to something unrelated, start over.

Plan-then-act, concretely

For anything beyond a one-liner, split the work in two:

Before you change any files: read R/01_clean.R and data/raw/cohort.csv,
then tell me your plan for the cleaning step and exactly which files
you'll create or modify. Wait for my OK.

Review the plan. Then:

Looks good — go ahead. Make the changes on a new branch and show me
the diff before we commit.

This is the loop we’ll formalize with git in the next module.

CLAUDE.md: standing instructions for your project

Repeating “use tidyverse, keep it readable, the data lives in data/” every session is a waste. Put durable facts and preferences in a CLAUDE.md file at the root of your project. Claude Code reads it automatically at the start of every session — it’s persistent context.

A good research CLAUDE.md covers:

# Project: <name>

## What this repo does
One paragraph: the research question and what the code produces.

## Structure
- `data/raw/`    — never edit; source data
- `data/clean/`  — generated by scripts in R/
- `R/`           — numbered pipeline: 01_clean.R, 02_model.R, 03_figs.R
- `figs/`, `tables/` — outputs

## How to run
`source("R/00_run_all.R")` reproduces everything from raw data.

## Conventions
- Language: R (tidyverse). Readable over clever.
- Style: snake_case; one function per task; comment the *why*.
- Figures: colorblind-safe palette; 300 dpi; labelled axes.

## Guardrails
- Never modify anything in data/raw/.
- Don't install packages without asking.
- Make changes on a branch; I review diffs before merging.
NoteCLAUDE.md vs. a skill (preview)

CLAUDE.md = standing context for this project, read every session. A skill (Module 4) = a reusable procedure for a recurring task, invoked when relevant. You’ll write one of each today.

You keep a global CLAUDE.md too (mine lives at ~/.claude/CLAUDE.md) with facts true across all your work — who you are, your stack, your figure preferences. Project files add the specifics.

Reviewing output like a reviewer

Treat the agent’s output like a manuscript you’re reviewing:

  • Does it answer the question I asked? (Not a nearby one.)
  • Is the diff minimal and legible? Big surprise diffs are a red flag.
  • Did it verify? Tests run? Output sane? Row counts right?
  • Would I be comfortable explaining this in a methods section? If not, ask why it did it that way.
WarningHallucinated specifics

Agents can invent a function argument, a package, a parameter value, or a citation that looks right. Any factual claim — a coefficient, a dose, a reference — gets verified against the source, not accepted because it’s fluent.

What to remember

  • A prompt = goal + context + constraints + done-condition.
  • Plan before acting, work in small steps, and make the agent show its work.
  • One session, one task — start fresh when you switch.
  • Put durable project facts in CLAUDE.md so you stop repeating yourself.
  • Review output like a critical reviewer; verify every factual specific.
